## <img src="assets/icons/about.svg" width="19" alt=""> About my work

I'm a computer science graduate working across software engineering, cybersecurity, and DevSecOps. I spent six months as a cloud and DevOps intern — configuring environments, validating builds and releases, and deploying services across AWS, Azure, and GCP — and that is where the problem I work on now stopped being theoretical. Most of what goes wrong in a deployed system isn't inside any one component. It's in the space between components, and that space usually has no owner.

My work follows from that: **understanding how a code change affects the security of the connected components and the environment they run in.** Conflicting assumptions, incompatible interfaces, transitive dependencies, permissions, and configuration drift are the failures I find most interesting, because every one of them passes the checks aimed at a single file.

I'm particularly interested in validating open-source contributions — including those written with AI assistance — by examining the changed code alongside the services, dependencies, and configurations it can reach. That means treating the whole path as one system: development, pre-production testing, CI/CD, and the production environment the change eventually lands in.

## <img src="assets/icons/journey.svg" width="19" alt=""> My journey to computer science

> Aviation came first. I wanted to fly, and for a long time the plan was aeronautics, not software. What changed it was opening a flight simulator to see what was underneath — and finding that the underneath was the part I enjoyed most.

<img src="assets/journey.svg" width="100%" alt="A climb from writing programs in 2018, to opening the simulator files in 2020, to shipping into the engine by 2021, to reading the engine&apos;s own language by 2022, with a dashed branch marking the aeronautics path not taken.">

**Before 2020 &mdash; the exam language and the working language.** I had been writing C and C++ since around 2018, before either was on a syllabus. School later taught C++, C and Java together and the board required one of them: I took Java. C and C++ stayed the languages I actually built things with.

**2020 &mdash; the simulators open.** I found simulation games, and then found that they could be opened. An aircraft inside a simulator is not a fixed part of the product; it is a set of files somebody authored, in formats somebody documented, loaded by an engine somebody wrote.

**2020&ndash;2022 &mdash; building for them.** Blender and Photoshop, both self-taught, and then real work shipping into six platforms. Every engine wanted the same idea in a different form, and that turned out to be the whole education.

**2022 &mdash; the fork.** Pilot, or computer science. I chose computer science, because the part of aviation I kept returning to was the system underneath it &mdash; and that part is code.

**2022&ndash;2026 &mdash; B.Tech, Computer Science and Engineering.** The degree followed the curiosity rather than the other way round.

<details>
<summary>What I built, engine by engine &mdash; and what taught me the pipeline</summary>

#### Euro Truck Simulator 2 &middot; American Truck Simulator

<sub>Prism3D &mdash; SCS Software, written entirely in C++</sub>

**What I built.** Custom rendering and HDRI skyboxes &mdash; graphics work that changes how the entire world is lit rather than how one object looks &mdash; and a set of truck mods. I taught myself 3D from nothing to do this; there was no course behind it.

**How it gets there.** Prism3D never loads a mesh directly. Models go out through SCS Blender Tools, a Python add-on for Blender, as `.pim` geometry alongside `.pit` traits, `.pic` colliders and `.pia` animation, and those get compiled into the `.pmg` and `.pmd` binaries the game actually reads. Everything the game needs to *know* about a mod &mdash; what it is, where it attaches, which textures it uses &mdash; is declared separately in `.sii`, SCS's own unit-definition language, with `.tobj` descriptors pointing at the textures. Sky and climate live in that same declaration system, which is why a lighting overhaul is a data change rather than a code change.

#### Microsoft Flight Simulator 2020 &middot; 2024

<sub>Asobo in-house engine &middot; SDK in Developer Mode</sub>

**What I built.** Livery paint schemes, custom navigation and routes, and three airports &mdash; Mumbai, Nashik and Chennai.

**How it gets there.** A livery is not a repaint of the aircraft; it is a variation registered in `aircraft.cfg` under its own `[FLTSIM.N]` entry, with a `texture.cfg` naming fallback folders so anything the livery does not override falls through to the base aircraft. The surfaces you are actually painting are PBR maps &mdash; albedo, comp and normal &mdash; authored against the glTF model, and the compiler turns `.gltf` into `.glb` and the source PNGs into `.ktx2`. Airports are a different pipeline entirely: a scenery project in the SDK's Project Editor, edited in place in the Scenery Editor, then handed to the Package Tool, which invokes the BGL compiler to turn XML and shapefiles into the `.bgl` files the simulator loads.

#### X-Plane 11 &middot; 12 and Prepar3D

<sub>Laminar Research &middot; Lockheed Martin</sub>

**What I built.** The same three airports again for both platforms, an A320neo converted to run in each, and work on the flight mechanics and instrument clusters.

**How it gets there.** The same airport is a completely different artefact in each. X-Plane airports are authored in WorldEditor &mdash; Laminar's CAD-like editor &mdash; writing `apt.dat` at version 850 or higher, with scenery objects as OBJ8; aircraft are `.acf` files from Plane Maker, instruments read and write datarefs, and anything past that is a plugin against the XPLM C API. Prepar3D works in MDL, where the exterior model and the virtual cockpit are two *separate* MDL files &mdash; which is precisely what makes an aircraft conversion non-trivial &mdash; and gauges are authored in XML with C++ underneath when XML runs out.

The A320neo conversion was the clearest lesson in all of it. The same aircraft is a `.pmg` in one engine, a `.glb` in another, an `.acf` in a third and an MDL in the fourth — and the geometry is the easy part. What breaks is everything the geometry is *attached* to: the animations, the collision shapes, the instrument bindings, and each engine's private assumptions about what a control surface even is.

## <img src="assets/icons/research.svg" width="19" alt=""> Research areas

My central question: **How can DevSecOps help uncover security weaknesses between components that pass their individual checks, before those components reach production together?**

| Research area | Questions I want to investigate |
| :--- | :--- |
| **Contribution impact &amp; code validation** | How can we trace the direct and indirect effects of a contribution, then validate the affected code, interfaces, dependencies, and security assumptions before integration? |
| **Component interactions &amp; hidden dependencies** | Can a shared library, gateway, identity service, or other third component create a security weakness between services that appear unrelated or work correctly in isolation? |
| **Cross-stack compatibility &amp; configuration** | Where might languages, frameworks, or services disagree about data formats, input validation, identity, or permissions? How can we test those boundaries and their configuration together? |
| **Pre-production system validation** | How can integration tests, threat modeling, and adversarial test cases evaluate the connected system in an isolated environment that represents its intended production configuration? |
| **DevSecOps, MLOps &amp; deployment environments** | How can pipelines check application code alongside infrastructure, secrets, network access, dependency versions, and runtime settings, and make unresolved findings visible before release? |
| **Version changes &amp; continuous feedback** | How can supported, patched technology stacks be kept compatible as they evolve? How can runtime findings improve the checks applied to later changes and upgrades? |

<details>
<summary>How I work on these</summary>

| Commitment | What it means in practice |
| :--- | :--- |
| **Start with the smallest system that shows the problem** | A two-service test bed behind a real gateway is worth more than a survey of everything that could go wrong. If I cannot reproduce the failure on a machine I control, I do not yet understand it. |
| **Define the check before running it** | What counts as a finding, what counts as a false positive, and what the check cannot see &mdash; written down before the experiment rather than fitted to the result afterwards. |
| **Compare against the tools that already exist** | A result only matters if it surfaces something SAST, SCA, or an IaC scanner missed on the same input. The baseline is run on every experiment, not assumed. |
| **Publish the limitations with the result** | Every method here has a blind spot. Naming it precisely is usually the more useful half of the contribution, and it is what makes the next experiment possible. |

</details>

The next section takes two of these rows — component interactions, and cross-stack compatibility — as far as a specification, using exactly this method.

## <img src="assets/icons/idea.svg" width="19" alt=""> An idea I want to explore

Those two questions, taken as far as a design: **a pipeline stage that checks how a system fits together, not only what changed inside it.**

A dependency scanner reads the manifest, a SAST tool reads the diff, an IaC scanner reads the Terraform. Each is correct inside its own boundary, and none of them owns the space between boundaries — so a change can pass every gate and still be unsafe beside the services it talks to or the environment it lands in. Concretely: a Python service normalises an email address before an authorization lookup, the Java service behind the same gateway does not, and the mismatch exists only between them.

<details>
<summary>The four stages</summary>

| Stage | What it does | What it produces |
| :--- | :--- | :--- |
| **1 &middot; Map** | Builds a component graph for the change: services, interfaces, shared libraries, configuration, and the identity path | The blast radius of a diff, indirect edges included |
| **2 &middot; Test** | Exercises the assumptions on each edge &mdash; data shape, validation, authentication, permissions, error and timeout behaviour | A verdict per edge, not per file |
| **3 &middot; Validate** | Resolves the change against the environment it will land in: runtime and dependency versions, network policy, secrets, permissions | A compatibility verdict for the upgrade, not only the code |
| **4 &middot; Decide** | Reports what was tested, what failed, and what could not be reached | A release gate that names its own blind spots |

</details>

It consumes what SAST, SCA, and IaC tools already produce rather than replacing them, and everything happens before release. **What would tell me it works:** cross-component defects caught before merge that those tools miss on the same input — judged against the false-positive count, because a gate that cries wolf gets disabled within a week. The hard part is the graph itself; dynamic dispatch, configuration-driven routing, and service discovery are largely invisible to static analysis, so it is only ever as good as what it can see.

**Where it stands:** design stage. I'm developing the component-mapping and environment-validation pieces inside VulnScanner and Netra, and this is the specification I would prototype against.
